# mutation-probe — подсадка, доказывающая свой приход

Отрицательный контроль теста («сломай защиту — тест обязан покраснеть») проверяет
собственную постановку так же слепо, как обычный тест проверяет угрозу, — если не
доказано, что мутация ДОШЛА до предмета.

Живой случай, из которого средство выросло (07.08.2026): чинил перехват исключений,
написал подсадку, прогнал — тест зелёный. Вывод напрашивался: защита не ловит. На
деле подсадка не применилась, якорь совпал не с тем местом: строк `except Exception
as exc:` в файле оказалось 21. Зелёный тест означал третье состояние, для которого
признака не было: «проба до предмета не дошла».

## Четыре состояния вместо двух

| статус | код | что значит |
|---|---|---|
| `UNVERIFIED` | 2 | мутация не доказана в целевом месте — о защите НЕ ИЗВЕСТНО НИЧЕГО |
| `APPLIED` | — | не вердикт о защите, а подтверждённый факт применённости |
| `FAIL-SAFE` | 0 | мутация внесена, тест покраснел: защита ловит |
| `HOLE` | 1 | мутация внесена, тест зелёный: защиты на этот случай нет |

Зелёный тест при `UNVERIFIED` — не PASS и не FAIL, а отсутствие показания.

## Контракт

Требования, которые средство выполняет (формулировка Praxis, AbstractDL 07.08.2026):

- якорь замены обязан быть уникален — иначе отказ, а не лотерея;
- число совпадений печатается и попадает в квитанцию;
- хэш целевого участка до и после записывается;
- отдельная проверка ПЕРЕЧИТЫВАЕТ файл и подтверждает, что участок изменился;
- только затем запускается тест, который обязан покраснеть;
- восстановление файла подтверждается чтением, а не фактом вызова (`restore_check`).

## Квитанция

`--receipt r.json` пишет машиночитаемую улику: коммит репозитория, файл, якорь,
число совпадений, хэши до/после, команда мутации, команда теста, код возврата теста,
restore-check, итоговый статус. Смысл: `HOLE` перестаёт быть рассказом о дыре и
становится переносимой уликой, которую другой повторит и оспорит.

## Проверка самого средства

`fixture/` — крошечный предмет (проверка подписи + намеренно не покрытый тестом
лимит длины) и три команды, дающие три разных состояния. Смотри `fixture/README.md`.
Там же оставлен след моей ошибки: первый вариант третьего случая давал `FAIL-SAFE`
вместо ожидаемого `HOLE`, потому что fixture был собран по моему представлению о
покрытии, а не по факту. Обнаружилось прогоном — тем самым классом, ради которого
средство и сделано.

## Границы

- Подтверждает, что замена внесена в объявленное место, и НИЧЕГО не говорит о том,
  та ли это мутация по замыслу: выбор мутации остаётся за человеком и не проверен.
- Работает текстовой заменой по точному якорю. Мутации, которые вносятся логически
  (порядок вызовов, состояние в рантайме, гонки), им не берутся.
