# КАК поставить и под что править

## Что лежит в пакете

```
code/file_safety_check.py    — статический гейт + AV + честная метка + журнал (фазы 2,3,5,7)
code/intake_poller.py        — приём файлов из супергруппы: getFile → incoming/ → воркер → ответ в тред
code/triage_daemon.py        — демон LLM-триажа: inbox → конвертер при необходимости → ридер → outbox
code/md_convert.py           — одноразовый PDF/DOCX/HTML → Markdown + картинки в ZIP (uid fs-triage)
code/triage_reader.py        — обезвреженный ридер под отдельным uid (одноразовый, без памяти)
code/README-iz-deploya.md    — README боевого экземпляра (⚠ отстал, см. «Расхождения» ниже)
```

## Зависимости

- python3 (стандартная библиотека; сторонних пакетов воркер не требует),
- `file` (magic-байты) и `clamscan` — иначе AV-ступень честно отдаёт `SKIPPED:not-installed`,
- для конвертации PDF — `pdftotext` и `pdfimages` (poppler); DOCX/HTML — `pandoc`
  с поддержкой `--sandbox`. Нет инструмента — `convert_tool_missing:<имя>`, ридер не вызывается,
- для триажа — доступ к какой-нибудь модели (у нас это внутренний «котёл»; в ридере это одна
  функция, меняется под свой эндпойнт),
- systemd, если ставить демонами.

## Порядок

1. **Отдельный хост или хотя бы отдельный пользователь.** Канон: `/opt/<узел>/file-safety/`,
   владелец — системный пользователь без shell, каталоги `incoming/` и `quarantine/` с правами
   700. Недоверенное не должно стоять рядом с вашими ключами.
2. **Воркер сам по себе** — проверить до всякой обвязки:
   `runuser -u file-safety -- python3 file_safety_check.py <path>`
   Код возврата: 0 = `quarantine`, 1 = `reject`. Рядом с файлом появится `<path>.safety.json`.
   ⚠ Каталог должен быть записываем для пользователя воркера, иначе метка не ляжет, а вы решите,
   что дело в файле (поймано на себе при приёмке 22.09).
3. **Приём из чата.** Свой бот (privacy off), токен кладётся ТОЛЬКО на этот хост, файлом с
   правами 400 рядом с поллером. Адрес группы — переменная окружения `MYCELIUM_GROUP_ID`
   (в боевом экземпляре стоит id нашей супергруппы; в пакете вынесен намеренно).
4. **Триаж.** Отдельный uid, наружу закрыт правилами iptables по owner-match — разрешён ТОЛЬКО
   адрес модели. Грабля, оплаченная нами: правила надо ставить В НАЧАЛО цепочки OUTPUT, иначе их
   обходит ACCEPT от ufw, и трафик утекает молча.
   Для действующего сервера r4 сохраняет все группы и существующие права.
   Приём должен уже состоять в fs-triage, чтобы назначать эту группу свежим входам.

## Обновление #2387: md.zip в чат (root, только приём)

После вердикта приём прикладывает существующий `<qdest>.md.zip` размером ≤50 МиБ
ответом на исходное сообщение в той же теме. Имя вложения — имя оригинала
с суффиксом `.md.zip`; подпись напоминает, что это недоверенные данные. Для большего ZIP
вердикт явно сообщает, что файл в чат не отправлен. Ошибка sendDocument даёт `[warn]`
в журнале службы и отдельное короткое сообщение; offset продолжает двигаться.

С #2501 (12.11.2026) у файла два имени. На диске — прежнее строгое: всё, кроме латинских букв,
цифр, точки, дефиса и подчёркивания, заменено на «_». У вложения в чате сохраняются буквы, цифры
и комбинирующие знаки любого письма; кавычки, слэши, управляющие и невидимые символы заменяются
на «_», основа имени не длиннее 180 байт. Чего это не обещает: Telegram сам дочищает имена
с нелатинскими буквами (на живом файле точки внутри имени стали подчёркиваниями), а md-файл
внутри архива назван по имени на диске. Похожие буквы разных алфавитов не различаются.

Для сервера с уже установленным #2350 доставить пакет локально и запустить:

```bash
bash tests/deploy_2387.sh "$PWD/code"
```

Рецепт **не выполнялся при разработке**. Он меняет только `intake_poller.py`,
сохраняет его uid/gid/mode и ненулевой литеральный GROUP_ID из действующего файла
проверками r4. Все проверки исходника, команд, доступа к журналу, очередей, offset,
служб и места в `/root` выполняются до stop. Бэкап, подготовленный поллер, манифест,
снимок состояния и автономный откат сохраняются в
`/root/md-zip-2387-<timestamp>-<pid>/` и проверяются до READY и stop.

Затем stop только `mycelium-intake` → drain/сверка состояния средствами r4 при
работающем worker → атомарная замена поллера → сверка SHA256/атрибутов/GROUP_ID →
start приёма → наблюдение active в течение 30 с и проверка журнала с момента запуска
на traceback → повторная сверка файла. Worker и конфигурация systemd не меняются.
При ошибке печатаются фаза, состояние приёма, бэкап и команда отката; временный файл
убирается при ERR/INT/TERM. Автоматического запуска после неудачной установки нет.

Откат: `bash <backup>/rollback_2387.sh <backup>` — сначала проверяет бэкап, затем
останавливает только приём, возвращает прежний поллер с атрибутами, сверяет SHA256
и GROUP_ID, запускает приём и повторяет 30-секундную проверку. Offset, очереди и
журнал не восстанавливаются; прерванная при stop задача требует сверки снимков,
как описано для r4 ниже. Рядом со скриптами нужны `2387_common.sh`, `r4_common.sh`,
`deploy_2387_lib.py` и `deploy_r4_lib.py`; откат получает их в своём бэкапе.

Локальные проверки без токена/сети/настоящего systemd:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 tests/intake_2387_cases.py
PYTHONDONTWRITEBYTECODE=1 python3 tests/intake_2387_mutations.py
PYTHONDONTWRITEBYTECODE=1 python3 tests/deploy_2387_cases.py
```

В модели с `MD_R4_TEST_ROOT` 30 проверок active выполняются без задержки;
настоящие 30 с и Bot API проверяются только при разрешённом оператором выкате.

## Обновление #2350 r5 на существующем сервере (root)

Рецепт полного обновления #2350: `tests/deploy_r4.sh`, откат: `tests/rollback_r4.sh`.
Оба используют соседние `r4_common.sh`, `deploy_r4_lib.py`; проверка — `check_deploy.py`.
Доставить пакет локально; запуск из его каталога (без MD_R4_TEST_ROOT):

```bash
bash tests/deploy_r4.sh "$PWD/code"
```

Меняются только `fs-triage/{triage_daemon.py,md_convert.py}` и `file-safety/intake_poller.py`
под `/opt/mycelium`. uid/gid/mode заменяемых файлов берутся из lstat перед обновлением;
новый md_convert.py получает атрибуты triage_daemon.py. Файлы ставятся через install
во временное имя и mv в том же каталоге. Если отсутствуют, создаются только work
(fs-triage:fs-triage 0700) и outbox/.rejected (fs-triage:fs-triage 0770).
Несовпадающие права существующих каталогов означают отказ, без исправления chmod/chown.

Границы служебных записей рецепта: каталог бэкапа
`/root/md-convert-2350-<timestamp>-<pid>/` содержит также подготовленную копию поллера,
манифест, снимки и автономный откат; отсутствующий
`/etc/systemd/system/fs-triage-worker.service.d` создаётся с mode 0755.
В каталогах целевых файлов и drop-in временно создаются `<target>.r4.XXXXXXXX`;
рецепт и откат удаляют собственное временное имя при ERR/INT/TERM (SIGKILL и потеря
питания trap не исполняют). Проверочные Python-команды рецепта и отката работают
с `PYTHONDONTWRITEBYTECODE=1`. Сама перезапущенная служба может создавать обычный
`/opt/mycelium/fs-triage/__pycache__/` при импорте md_convert. Службы продолжают
штатные записи в очереди, quarantine, журнал и offset.

Единственная конфигурация службы —
`/etc/systemd/system/fs-triage-worker.service.d/md-convert-work.conf`:

```ini
[Service]
TemporaryFileSystem=/opt/mycelium/fs-triage/work:rw,nosuid,nodev,noexec,size=256M,nr_inodes=4096,mode=1777
```

Mount виден только в namespace службы и исчезает вместе с ним. 1777 позволяет fs-triage
писать в root-owned корень нового tmpfs без зависимости от поддержки uid=/gid= данной
версией systemd. На хосте work остаётся 0700; другие службы этот mount не получают.
Это ограничение work, а не квота всего uid. До выката владелец проверяет строку на сервере:

```bash
systemd-run --wait -p User=fs-triage \
  -p TemporaryFileSystem=/opt/mycelium/fs-triage/work:rw,nosuid,nodev,noexec,size=256M,nr_inodes=4096,mode=1777 \
  sh -c 'findmnt --mountpoint /opt/mycelium/fs-triage/work --output TARGET,FSTYPE,OPTIONS; touch /opt/mycelium/fs-triage/work/x && df -h /opt/mycelium/fs-triage/work && df -i /opt/mycelium/fs-triage/work'
```

Перед любым stop рецепт проверяет обычные файлы и цепочки родителей через lstat,
отвергает symlink/hardlink, проверяет drop-in и его каталог, ≥50 MiB свободно в /root,
непустой целочисленный offset и active обеих служб. Проверяет доступность команд,
включая install, mv, mktemp, nsenter, findmnt, systemctl, python3. До stop читает все
имеющиеся quarantine/*.safety.json как JSON, проверяет verdict и перечисляет непригодные
метки и остатки: incoming (кроме архивных reject-меток), dot-файлы inbox, outbox кроме .rejected.
Обычный непустой inbox допускается для согласованного drain. При известном блокере —
отказ до stop; эти проверки повторяются после stop intake и после stop worker.

Из ДЕЙСТВУЮЩЕГО intake_poller.py извлекается `^GROUP_ID\s*=\s*(-?\d+)\b`:
ровно одно совпадение и ненулевое значение, иначе отказ до stop с диагностикой.
В копии пакетного поллера ровно одна строка с MYCELIUM_GROUP_ID заменяется литералом
с извлечённым id. AST и компиляция всего подготовленного текста без исполнения,
токена и сети проверяют единственное литеральное присваивание GROUP_ID с этим значением.
Id и SHA256 подготовленной копии входят в манифест. Сохранённая в бэкапе
`prepared-intake_poller.py` ещё раз проверяется до READY; устанавливается именно она,
а check_deploy отдельно сверяет GROUP_ID установленного файла с манифестом.
Environment приёма и второй drop-in не нужны и не добавляются.

Рецепт печатает план и сохраняет исходные
uid/gid/mode, SHA256, копии обычных файлов (cp -p), прежний drop-in либо его отсутствие,
исполняемый откат и снимки состояния в `/root/md-convert-2350-<timestamp>-<pid>/`.
Ошибка подготовки не останавливает службы. ERR/INT/TERM печатают фазу, оба состояния,
путь бэкапа/готовность и точную команду отката.

Затем: stop intake → до 300 с дренирования inbox работающим старым демоном →
повторная проверка offset → stop worker → установка → создание каталогов → drop-in →
daemon-reload → start worker → active и findmnt через nsenter его MainPID → start intake →
active и offset, равный значению после дренирования → check_deploy по манифесту.
Исходники очереди удаляются демоном в finally; пустой inbox означает завершение обработки
этих источников, но не доставку результата поллеру.

После остановки intake сохраняются инвентари inbox/outbox/incoming/quarantine, offset
и копия журнала. Изменение quarantine/журнала/архивных reject-меток во время stop или повреждённая JSON-метка требуют ручной
сверки и прерывают установку. Неразобранный inbox по таймауту, dot-partial/kind, incoming или готовый
outbox без потребителя прерывают установку с диагностикой. `.rejected` разрешён:
это уже отвергнутые данные, не незавершённые задачи. Архивные reject-метки в incoming (обычные файлы без ссылок ≤64 КиБ, JSON-объект с verdict reject, без данных рядом) допустимы, поскольку приём оставляет их как журнал отказов после удаления данных.
Для сверки сравнить state-before-stop,
state-drained (либо state-drain-timeout), state-stopped и сохранённые offset/journal с
метками/оригиналами quarantine. Завершить привязку результата к метке либо явно оформить
повтор для конкретного update; ничего не переименовывать в очередь вслепую.
Пустой/невалидный offset никогда не заменяется нулём. Снимки не подставляются обратно
поверх новых данных при откате. Старый intake не имеет graceful SIGTERM: остановка
может оборвать текущую операцию; сверка остатков и изменений задач обязательна.

Откат запускается точной командой, напечатанной рецептом, например:

```bash
bash /root/md-convert-2350-<timestamp>-<pid>/rollback_r4.sh /root/md-convert-2350-<timestamp>-<pid>
```

Он проверяет готовность бэкапа, останавливает intake и worker, возвращает прежние файлы
через временные имена (новый md_convert.py удаляет), удаляет r4 drop-in и возвращает
прежний, если тот существовал; daemon-reload → start worker → start intake → оба статуса.
Runtime-пути, группы и права не восстанавливает и не меняет. Созданные пустые каталоги
могут остаться. Отказ любого шага даёт nonzero, фазу и состояния; после частичной установки
рецепт не запускает смешанный комплект автоматически. Таймаут drain оставляет intake
остановленным, worker — работающим; откат кода не заменяет сверку задачи.

Read-only проверка установленного r4:

```bash
python3 -B tests/check_deploy.py --backup /root/md-convert-2350-<timestamp>-<pid>
systemctl show -p TemporaryFileSystem fs-triage-worker
```

Проверяются только три устанавливаемых файла (атрибуты из манифеста, содержимое),
work/.rejected, drop-in, эффективное TemporaryFileSystem и tmpfs в namespace worker
(size ≤256 MiB, nr_inodes ≤4096, mode=1777). Проверки прав ридера, гейта, токена,
родительских каталогов кода, новых групп и ReadWritePaths из r3 удалены.

## Отложено: ужесточение прав (не выполнять)

Перестройка групп, владельцев/режимов кода и каталогов, ReadWritePaths служб и /etc/fstab
вынесена в отдельный техдолг со своим ревью. Рецепт r3 из этого файла удалён; REPORT3 §5
исторический и отменён решением владельца. Возвращаться к его командам при r4 нельзя.
Сюда же относятся реальная проверка handoff между uid при изменённых группах и проверка
rename incoming→quarantine в изменённом mount namespace (R3-1/R3-2).

## Протокол и пределы

Приём публикует скрытый .<name>.kind перед файлом через dirfd, O_EXCL/O_NOFOLLOW и
случайные имена. До записи/публикации обоим новым fd назначает gid fs-triage через
fchown(-1, gid); отсутствие группы или отказ fchown явно отказывает handoff.
Демон публикует ZIP до JSON; converted остаётся в метке только при принятом ZIP.
Архив недоверенный: тип/uid/размер проверяются, внутренности поддельного ZIP после
захвата producer — нет. Результат не повышает quarantine. Флаги ограничены белым списком,
ASCII-шаблоном и 12 записями; ответ — 3500 символами. Приём переносит отвергнутое в
.rejected, демон убирает до 128 объектов / 0,2 с на круг. Общей квоты .rejected/quarantine нет.

Конвертация: 200 страниц, 200 media, 50 MiB выхода, общий рабочий дедлайн 60 с;
ридер отдельно 90 с, приём ждёт 170 с. Перед запуском конвертера statvfs work требует
≥100 MiB доступного места; обычная файловая система тоже поддерживается.
Скан /proc строит индекс parent→children, обход линеен с проверками времени внутри
обхода. Скану выделено до 1 с; после него известным PID выделяется отдельный бюджет
сигнализации/неблокирующего waitpid до 1 с, даже если срок скана истёк. Цикл повторов
имеет бюджет 2 с; последний этап сигнализации может выйти за него на свой бюджет.
Неопределённость даёт convert_cleanup_unknown и ok=false. Это кооперативные дедлайны
этапов, а не обещание завершения всей convert за 4 с: файловая уборка и аварийный
proc.wait демона не имеют такого ограничения; системные вызовы тоже не прерываются
Python-проверкой monotonic. PPID-снимки, аварийный killpg и общий uid не дают гарантии cgroup;
внешний владелец жизненного цикла/отдельный uid остаются техдолгом.

## Что менять под себя

- `FILE_SAFETY_MIME_EXTRA` — точные MIME-типы через запятую для расширения белого списка на время вызова, без изменения умолчаний пакета.
- вайтлист типов, потолок размера, квоты zip — константы в начале `file_safety_check.py`
  (`MIME_WHITELIST_*`, `MAX_FILE_SIZE_BYTES`, `ZIP_MAX_*`), не в логике;
- модель и промпт триажа — `triage_reader.py`;
- адрес группы и путь к токену — окружение и файл рядом с поллером.

## Приёмка: как убедиться, что оно живое, а не просто установленное

Мутацией, а не чтением логов. Кладёте файл с тестовой строкой EICAR и чистый файл рядом:

```
eicar → verdict reject,     av INFECTED:Eicar-Test-Signature, код 1
clean → verdict quarantine, av clean,                         код 0
```

Если AV не установлен, метка честно скажет `SKIPPED:not-installed` — и это НЕ «чисто».
Прогон на нашем боевом экземпляре 22.09 10:3xZ дал ровно эти две строки.

Полный регресс — 12 случаев: pdf→q, EICAR→r, обычный zip→q, вложенный zip→r, превышение
размера→r, симлинк→r, чистый png→q, полиглот→r, данные после терминатора→r, FIFO→r, jpg→q, txt→q.

Docx (с 03.11.2026) — отдельный набор, 87 случаев, каждый с ожидаемой ПРИЧИНОЙ отказа, а не только
исходом: `python3 tests/docx_cases.py <пустой каталог для фикстур> code/file_safety_check.py`.
Нужен `python-docx`. Случаи с исходом `quarantine` гоняют clamscan, весь набор идёт минут семь.
Сошлось — последняя строка `ИТОГ: все сошлись (87 случаев)`.

`PYTHONDONTWRITEBYTECODE=1 python3 tests/md_convert_r4_cases.py` и
`PYTHONDONTWRITEBYTECODE=1 python3 tests/deploy_r4_cases.py` и
`PYTHONDONTWRITEBYTECODE=1 python3 tests/deploy_r5_cases.py`. Два последних набора моделируют
службы и mount через PATH и временные каталоги, не проверяют настоящий systemd. Фикстуры строятся во временных каталогах; случаи,
которым недостаёт внешнего инструмента, печатают `SKIP` с причиной. Для сервера:
`bash tests/server_smoke.sh` — PDF/DOCX/HTML под текущим uid, JSON конвертера и список ZIP;
временные файлы удаляются при выходе, ничего не устанавливается.

Открытый вопрос: конвертер под fs-triage имеет те же права на `.cauldron_key`, что и ридер.
Ключ работает только через 127.0.0.1:4000. Отдельный uid конвертера без ключа
строже, но отложен в техдолг и требует отдельного запуска процесса,
прав на передачу входа/выхода и отдельной сетевой политики; этим изменением uid не разделены.
