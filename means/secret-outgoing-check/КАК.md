# КАК: поставить проверку секретов на выходе

Порядок важен: сначала опись путей, потом двери. Дверь, поставленная без описи, стоит там,
где вспомнили.

## Шаг 1. Опись путей наружу

**Что закрываем.** Текст или файл, написанный моделью, уходит стороне разговора — человеку,
другому агенту, на публичную страницу, в репозиторий — и несёт значение секрета.

**Что сюда не входит.** Канал к провайдеру модели: туда по устройству уходит весь контекст, и
проверка на выходе этого не меняет. Резервные копии на ваши же машины — отдельное решение.

**Как искать.** Не по памяти, а по коду и настройкам:

- вызовы сети в своих скриптах: `requests`, `httpx`, `aiohttp`, `urllib`, `smtplib`, `curl`,
  клиенты мессенджеров;
- инструменты агента, которые что-то отправляют: ответ в чат, письмо, голос, публикация
  документа или страницы, веб-запрос, поиск (адрес и запрос — тоже канал вывоза);
- задания по расписанию и службы, которые шлют сами, без агента в разговоре;
- удалённые репозитории и всё, что делает `git push`, включая задания по расписанию;
- автоматизация браузера;
- команда оболочки: в неё можно вписать и текст, и путь к файлу.

**Что решить по каждому пути.** Одно из трёх, письменно:

- *закрыть* — и какой дверью;
- *исключить* — с причиной. Годятся: текст собирает скрипт по шаблону, свободного текста модели
  в нём нет; адресат — ваша же машина; адресат — провайдер модели. Не годится: «этим путём
  почти не пользуюсь»;
- *проверить до решения* — если не знаете, например, приватен ли репозиторий.

**Где ставить дверь.** Точек три вида, и чем их меньше, тем лучше:

- *общая очередь отправки.* Если всё исходящее в мессенджер идёт через одну функцию — одна
  проверка в ней закрывает все пути через неё, включая те, что появятся позже;
- *хук харнесса на исходящие инструменты.* Закрывает то, что идёт мимо вашей очереди: встроенные
  ответы в каналы, почту, веб-запросы, команды оболочки;
- *проверка в самом скрипте* — для одиночных публикаторов, которые не идут ни через очередь,
  ни через инструменты агента.

**Предел описи.** Она даёт нижнюю границу. Запишите рядом, где могли пропустить, — это список
того, что смотреть в следующий раз.

У автора опись заняла один проход поисковым агентом (около пятидесяти вызовов, только чтение)
и сверку с прежним списком; итог — три десятка с лишним позиций: примерно половина закрыта
тремя точками, вторая половина исключена с причиной, две позиции остались техническим долгом.

## Шаг 2. Хранилище и ядро

Положите каталог `code/` куда удобно; файлы в нём должны лежать рядом друг с другом — двери
ищут ядро `secret_scan.py` в своём же каталоге.

Откуда ядро берёт значения:

- по умолчанию — из `~/secrets` (все файлы, с подкаталогами и каталогами за символьными
  ссылками);
- иначе — из `SECRET_SCAN_ROOTS`: список файлов и каталогов через двоеточие;
- добавочные места вне хранилища — `SECRET_SCAN_EXTRA_GLOBS`: шаблоны относительно домашнего
  каталога через двоеточие. Сюда идёт, например, файл настроек расширения, в котором лежит ключ.

Если хранилище не в `~/secrets`, переменные должны стоять в окружении **каждого** процесса,
который зовёт ядро: клиента агента (для его хука), оболочки, из которой уходят коммиты,
вашего скрипта отправки, заданий по расписанию. Процесс без переменной молча возьмёт
умолчание — и при пустом `~/secrets` откажет, а при непустом будет проверять не то.

Что ядро считает значением секрета:

- строку `ИМЯ=значение`, если имя похоже на секрет (`KEY`, `TOKEN`, `SECRET`, `PASS`, `AUTH`…)
  и значение не короче восьми знаков;
- в файле, само имя которого похоже на секрет, — значение под любым именем, кроме явных
  несекретных сведений (`HOST`, `URL`, `USER`, `PORT`…);
- голую строку не короче десяти знаков и без пробелов;
- в JSON — строки под ключами с такими же именами.

Чего ядро значением НЕ считает, даже в хранилище:

- число из одних цифр: под секретным именем — короче восьми цифр, голой строкой — короче
  шестнадцати. Десятизначный код восстановления, записанный голой строкой, ядро не узнает;
  запишите его как `ИМЯ_CODE=…`;
- простой адрес `http(s)://…` без имени и пароля перед узлом и без длинной строки-ключа
  в хвосте — даже под секретным именем;
- слова `true`, `false`, `none`, `null`;
- строки, начинающиеся с `#`, `;`, `[` или `-----`;
- в JSON — числа и другие нестроковые значения;
- файл хранилища больше мегабайта.

Хвостовой комментарий после значения (` # сменён тогда-то`) отрезается, кавычки снимаются.

**Проверьте, что ядро не слепо, — описью.** Из каталога пакета:

```
python3 -B code/secret_scan.py --inventory
```

По каждому файлу хранилища опись показывает: сколько значений взято (`taken`), их метки
(`labels`) и сколько строк отброшено и почему (`skipped`): `short` — короткое, `short-number` —
число короче порога, `space` — голая строка с пробелом, `nonsecret-name` — имя не похоже на
секрет, `plain-address` — простой адрес, `comment`, `blank`, `literal`, `non-string`,
`file-too-large`, `unreadable`. Значения из хранилища не печатаются.

Пройдите по своим ключам: каждый должен найтись среди меток. Ключа нет — он лежит вне хранилища
или попал в `skipped`; такой ключ проверка не знает. Опись — только для чтения человеком:
отправку она не разрешает.

Двери зовут ядро в строгом режиме и отказывают (`DetectorBlind`), если хранилище пусто, если
заданного корня нет или если хоть один файл или каталог в нём не читается. Частично слепое
ядро считается слепым. Каталог за символьной ссылкой обходится, каждый настоящий каталог —
один раз; ссылка в никуда или в нечитаемый каталог — тоже отказ.

## Шаг 3. Двери

### Своя точка отправки — `guard.py`

```python
import sys
sys.path.insert(0, "/путь/к/secret-outgoing-check/code")
from guard import assert_clean

def safe_send(text, paths=(), allow=()):
    assert_clean(texts=[text], files=paths, allow=allow)  # до любого действия наружу
    return existing_send(text, paths)
```

`assert_clean` бросает `OutgoingSecretError` с метками (без значений из хранилища) или `DetectorBlind`, если
ядро слепо или частично слепо. Оба исключения значат одно: не отправлять. Передавайте
в `texts` всё, что уйдёт: текст, подпись к файлу, заголовок, имя темы. Одна строка вместо
списка считается одним текстом, один путь — одним файлом; байты не принимаются (`TypeError`) —
декодируйте их сами.

Чем меньше у вас функций отправки, тем лучше: одна общая закрывает и те пути, что появятся позже.

### Хук Claude Code — `hook_pretooluse.py`

Возьмите `settings.example.json` за образец: блок `hooks` из него переносится в файл настроек
клиента — `~/.claude/settings.json` (для всех проектов) или `.claude/settings.json` в проекте.
Путь-заглушку `/path/to/…` замените настоящим. `matcher` составьте по своей описи: встроенные
исходящие инструменты, инструменты ответа в каналы, веб-запросы, команда оболочки.

Если инструмент отправляет содержимое файла по пути, допишите его в словарь `FILE_PATH_KEYS`
вверху файла хука — иначе хук увидит путь, но не файл. Понимаются три формы входа: одна строка
с путём, список путей и словарь, у которого значения — пути либо словари с ключом `from`.
Другую форму хук не разберёт; такой инструмент закрывайте своей точкой отправки.

Как ведёт себя хук:

- нашёл значение — отказ (код 2), в сообщении метки. Проверяются все строки входа инструмента,
  имена полей и числа (число сравнивается в том виде, в каком оно записано во входе);
- для команды оболочки и веб-запросов одна метка не считается: заголовок закрытого ключа сам
  по себе встречается в тестах и документации. Точные значения ловятся и там;
- ядро недоступно, слепо или частично слепо — отказ для всего, кроме команды оболочки: она
  проходит с предупреждением, иначе чинить было бы нечем;
- файл, названный во входе инструмента, не читается или отсутствует — отказ: непрочитанное
  не значит чистое.

Предел: вход, который не разбирается как JSON, хук пропускает.

После установки проверьте в живом клиенте, а не только пробой пакета: положите фальшивый ключ
в своё хранилище и попросите агента отправить его встроенным инструментом. Должен прийти отказ.
Потом фальшивый ключ уберите.

### Хук git — `git_pre_push.py`

В каждом клоне, откуда уходит код. Сначала узнайте, где у этого клона на самом деле лежат
хуки, — это не всегда `.git/hooks`: каталог может быть переназначен настройкой
`core.hooksPath`, а в дополнительном рабочем дереве `.git` — файл, а не каталог.

```
git rev-parse --git-path hooks                      # фактический каталог хуков
mkdir -p "$(git rev-parse --git-path hooks)"        # каталога может ещё не быть
ls "$(git rev-parse --git-path hooks)/pre-push"     # нет ли там уже своего хука (ошибка «нет файла» — хорошо)
ln -s /путь/к/secret-outgoing-check/code/git_pre_push.py "$(git rev-parse --git-path hooks)/pre-push"
chmod +x /путь/к/secret-outgoing-check/code/git_pre_push.py
```

Если хук `pre-push` там уже есть, ссылку поверх не ставьте: вызовите `git_pre_push.py` из
существующего, передав ему те же аргументы и тот же стандартный ввод.

**Проверка установки обязательна** — без неё вы не знаете, вызывается ли хук. Во временной
ветке закоммитьте файл с фальшивым ключом из своего хранилища и попробуйте отправить ветку.
Должен прийти отказ с меткой. Потом ветку удалите, фальшивый ключ уберите.

Ссылка годится: хук находит ядро рядом с настоящим файлом, а не рядом со ссылкой.

Что проверяется: строки, добавленные в уходящих коммитах, — в том числе в промежуточном
коммите, если ключ потом удалили, и в коммите слияния (он сравнивается с каждым родителем).
Смотрится само содержимое файла: если в репозитории настроен преобразователь, который
показывает файл в сокращённом виде, хук его отключает.

Новая ветка. Что уже есть на удалённой стороне, хук спрашивает у неё самой (отдельное
обращение, до двадцати секунд), а не верит локальным сведениям: после смены адреса
репозитория они устаревают. Не ответила, ответила пустым списком или объявленных ею коммитов
у вас нет — проверяется вся история ветки. На большом репозитории первая отправка ветки от
этого дольше, и старый ключ в истории её остановит.

Пределы: сообщения коммитов, имена файлов и двоичные данные не проверяются. Двоичным
считается то, что двоичным считает git: текстовый файл, помеченный так в настройках
репозитория, тоже пройдёт мимо проверки. Отправка с ключом `--no-verify` хук обходит.

## Шаг 4. Намеренная выдача

Иногда ключ нужно отдать. Способ у каждой двери свой, общее одно: разрешается **метка**,
а не «всё», и выдача оставляет строку `secret-outgoing-check: intentional handout: <метки>`
в потоке ошибок. Направьте этот поток в свой журнал — без этого строка никуда не попадёт.

- **Своя точка отправки:** `assert_clean(..., allow=["secrets/файл:ИМЯ"])`. Метку берите из
  сообщения об отказе или из описи, не сочиняйте: метка, которой ядро не знает, ничего
  не разрешает.
- **Хук git:** `SECRET_SCAN_PUSH_ALLOW=метка git push` — на одну команду.
  Случай из выкладки 12.11: сам этот пакет несёт в тестах строку-заголовок закрытого ключа
  (без тела), и отправка его копии останавливается с меткой `format:private_key`. Это
  ожидаемо: убедитесь, что тела ключа нет, и отправляйте с этой меткой.
- **Хук Claude Code:** `SECRET_SCAN_ALLOW=метки` в окружении клиента. Это окружение задаётся
  при запуске клиента, а не на один вызов: пока переменная стоит, метка разрешена во всех
  вызовах. Ставит её человек, на время, и снимает сразу. Агенту с отказом от хука правильнее
  идти через свою точку отправки.

Как выглядят метки. `каталог/файл:ИМЯ` — для строки `ИМЯ=значение`; `каталог/файл:lineN` — для
голой строки номер N; `каталог/файл:сервис.token`, `…:tokens[0]` — для JSON, полным путём
ключей. Второе значение под тем же именем получает `#2`. Одной метке хранилища всегда
отвечает одно значение.

Метка не несёт значения из хранилища. Ключ JSON заменяется на `<key#N>`, если он сам равен
значению из хранилища, похож на ключ известного формата или на длинный токен. Имя поля
в текстовом файле заменяется на `<key#N>`, а имя файла или каталога — на `<file#N>`, если
они содержат значение из хранилища или похожи на ключ известного формата. Те же замены
действуют в описи и в сообщениях об ошибках, где названы пути.

Предел: длинное имя файла или поля само по себе не заменяется — иначе метки стали бы
нечитаемыми. Поэтому ключ неизвестного формата, которым назвали файл или поле и который
нигде не лежит как значение, пакет напечатает как обычное имя. Не называйте файлы и поля
хранилища значениями ключей.

Метка разрешает значение целиком: и его копию в соседнем файле хранилища, и совпадение того же
значения по формату. Другие секреты в том же сообщении по-прежнему останавливаются. Значение,
переданное вместо метки, — отказ, и в журнал оно не попадает.

Особый случай — метки вида `format:вид`. Их получает любой ключ, похожий на известный
формат; если он же лежит в хранилище, у него будет и своя точная метка. Форматная метка —
не одно значение, а целый класс: разрешив `format:github`, вы снимаете проверку по формату
и пропускаете в этом сообщении любой ключ такого вида, которого нет в хранилище. Ключи из
хранилища по-прежнему останавливаются по своим меткам. Чтобы отдать один ключ и не открыть
остальные, сначала положите его в хранилище — и разрешайте его собственную метку.

## Шаг 5. Пробы

```
python3 -m pytest tests -q          # модульные: 165 проходят, 2 пропускаются
bash tests/probe_planted.sh         # живая проба: три двери на подложенном ключе, 53 проверки
bash tests/mutation_probe.sh        # ломает проверку тринадцатью способами и ждёт, что проба упадёт
```

Все три работают на временном каталоге с фальшивыми значениями и вашего хранилища не касаются.
Для первой команды нужен установленный `pytest` — сам пакет обходится стандартной библиотекой,
две пробы на оболочке работают и без него.

Что сделать сверх них у себя:

- живую пробу в своём клиенте — по каждому пути из описи (см. шаг 3);
- прогон по журналу уже отправленного, если он у вас есть: узнаете, сколько раз проверка
  сработала бы, и что из этого было намеренной выдачей;
- правите код двери — добавьте мутацию в `mutation_probe.sh`. Зелёная проба без мутации
  говорит только о том, что проба запускается.

## Расхождения пакета с боевым экземпляром автора

Пакет собран из кода, который работает у автора с 8 ноября 2026 года, но не равен ему.

- **`guard.py` — выделенная обёртка.** У автора та же проверка встроена в общую очередь
  отправки мессенджера, а разрешение — поле команды, которое остаётся в очереди. Обёртка
  покрыта тестами и пробой пакета; в харнессе автора она не работала ни дня.
- **Отказ при слепом и частично слепом ядре** и **опись хранилища** добавлены при сборке
  пакета. В боевом экземпляре на день сборки их нет.
- **Метки** в пакете однозначны и не несут значений из хранилища (предел — в шаге 4).
  В боевом экземпляре на день сборки
  метка — `файл:ИМЯ` или `файл:line` без номера, и у двух значений она может совпасть.
- **Хук git** в пакете видит коммиты слияния, строки с началом `++`, отключает преобразователь
  содержимого и не верит устаревшим локальным сведениям об удалённой стороне. В боевом
  экземпляре на день сборки — нет.
- **Числа во входе инструмента** и **каталоги за символьными ссылками** проверяет только пакет.
- **Отсутствующий файл во входе инструмента:** в пакете — отказ, в боевом экземпляре на день
  сборки — пропуск.
- **Разрешение в хуке Claude Code** (`SECRET_SCAN_ALLOW`) есть только в пакете. У автора хук
  только отказывает, намеренная выдача идёт через очередь отправки.
- **Имена переменных окружения** изменены; жёстко заданный путь к файлу настроек расширения
  заменён на `SECRET_SCAN_EXTRA_GLOBS`.
- **Кто писал и кто проверял.** Сборку из боевых исходников делала по наряду автора другая
  модель; автор принимал: читал код, повторял прогоны, ломал пакет своими мутациями (девять
  за три круга; восемь заметила живая проба, одну — только модульные тесты: замену имён
  файлов живая проба не проверяет). Пакет дважды читала третья модель. В первый раз нашла
  десять дефектов, подтверждённых пробами; семь из них пришли из боевого кода автора, а не
  из сборки. Во второй — ещё восемь, помельче, и один из них внёс сам автор: убрал из хука
  константу, на которую ссылались тесты, и не перепрогнал их. Всё, что лежит в модели угроз,
  исправлено кодом за три круга; два замечания закрыты текстом этой инструкции. Пробы
  ревьюера повторялись после каждого круга.

## Чего здесь нет

Список того, что пакет не закрывает. Читать как перечень непроверенного, а не как планы.

- **Чувствительное, кроме ключей.** Адреса и имена ваших машин, домены, пути, имена учётных
  записей, телефон и адрес человека. Перечислимую часть можно отдать тому же ядру: положите
  значения в отдельный файл голыми строками, по одному на строку, и добавьте файл в
  `SECRET_SCAN_ROOTS`. Пределы, все по коду ядра. Голая строка короче десяти знаков
  значением не считается — короткий адрес или имя машины так не поймать. Голое число короче
  шестнадцати цифр тоже — номер телефона так не поймать. Голая строка с пробелом считается
  заметкой и пропускается — почтовый адрес человека так не поймать. Что из вашего файла
  ядро взяло, а что отбросило, покажет опись. Строка
  вида `ИМЯ=значение` берётся, только если имя похоже на секрет; `HOST=…` или `ADDR=…` ядро
  нарочно пропускает как несекретные сведения. Снижать пороги без границ слова не стоит: пойдут
  ложные остановки. И последнее: неперечислимое (провайдер, датацентр, устройство системы,
  «где именно слабое место») кодом не ловится вообще — только вниманием того, кто пишет.
- **Уровни адресата.** Общий чат, личная переписка с чужим человеком и разговор со своим
  человеком требуют разного. В пакете уровень один. Если будете делать: двери нужен признак
  публичности адресата; для личной переписки с чужим разумное правило — пропускать чувствительное
  значение, только если оно уже есть в собственных сообщениях собеседника в этом чате.
- **Фрагменты кода и устройство системы.** Хук на отправку коммитов ловит ключи в добавленных
  строках. Он не ловит то, что код рассказывает сам: внутренние адреса, версии, расположение
  частей. Для публичного репозитория это отдельная вычитка.
- **Файл, отправленный по пути из команды оболочки.** Хук видит текст команды, а файл, названный
  в ней по пути, не читает.
- **Автоматизация браузера.** Ввод своих учётных данных в форму входа — её штатная работа,
  поэтому на неё хук не ставится. Переход на чужой адрес с секретом в строке остаётся открытым.
- **Новые клоны репозиториев.** Хук на отправку коммитов живёт в каждом клоне отдельно; в новом
  его нет, пока не поставите. `git push --no-verify` его обходит.
- **Сжатое и закодированное.** Архив, документ со сжатыми потоками, base64 от ключа — не видны.
